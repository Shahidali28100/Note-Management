## Why

Notes currently have no tags: AB-1004 shipped `Note` with no tags field, explicitly noting "the `Tags` table doesn't exist until AB-1006 — note DTOs simply omit a tags field in AB-1004; AB-1006 adds it as its own delta." AB-1005 likewise deferred `GET /api/notes` tag filtering, noting "FRS-NOTE-008 (tag filtering) is out of scope here: the `Tags`/`NoteTags` tables don't exist until AB-1006." FRS-TAG-001 through FRS-TAG-004 and the FRS §14 / SDS §93 ticket-traceability table assign Tags to **AB-1006**, next in the strict AB-1001 → AB-1016 dependency chain. This proposal implements Tags CRUD, note-tag assignment, and the deferred `tagId` filter using the `Tags`/`NoteTags` tables already scoped in SDS §15/§16, resolving the ambiguities the FRS/SDS leave open for this ticket via the user-approved answers below (SDS §97 lists no "Open Technical Decisions" entry for AB-1006, so these were sourced directly from FRS-TAG-001..004 and clarifying questions).

## What Changes

- **POST /api/tags** — creates a tag owned by the authenticated caller. `name` (required, 1–50 chars after trimming) and `color` (required, `#RRGGBB` hex format) are the only accepted fields. `name` uniqueness is enforced **case-insensitively** per user (FRS-TAG-001: "unique within the user's scope") — a duplicate (case-insensitive) name for the same user is rejected `409 Conflict`. Responds `201 Created` with the new tag (id, name, color, noteCount: 0, createdAt, updatedAt).
- **GET /api/tags** — lists the caller's own tags as a **plain array** (no pagination envelope — tags are low-cardinality per user, unlike notes), each item including `noteCount`: the number of the caller's **active** (non-deleted) notes currently carrying that tag (FRS-TAG-004; deleted notes excluded from the count).
- **PUT /api/tags/{id}** — renames/recolors a tag owned by the caller; same validation as create, same case-insensitive uniqueness check (excluding the tag being updated). Ownership does not change (FRS-TAG-002). `404 Not Found` for a tag that doesn't exist or belongs to another user (no existence/ownership disclosure, matching the notes precedent).
- **DELETE /api/tags/{id}** — removes a tag owned by the caller. Deleting a tag does **not** delete associated notes (FRS-TAG-003); it removes the tag's `NoteTags` rows only. `204 No Content` on success; `404 Not Found` under the same missing-or-not-owned rule.
- **POST /api/notes** and **PUT /api/notes/{id}** — both now accept an optional `tagIds` array (defaults to empty when omitted). Every id in the array must reference a tag owned by the caller; if any id doesn't exist or isn't owned by the caller, the **entire request is rejected `400 Bad Request`** — same treatment as an invalid title/content, and consistent with never revealing per-id existence/ownership to a non-owner. Duplicate ids within the array are de-duplicated server-side. There is no cap on the number of tags a note may carry. The note's assigned tags fully replace prior assignments on update (matching the existing full-replace semantics of title/content on `PUT`).
- **All note response shapes** (`POST /api/notes`, `GET /api/notes/{id}`, `PUT /api/notes/{id}`, `POST /api/notes/{id}/restore`, and each item in `GET /api/notes`) now include a `tags` array (`{ id, name, color }` per tag) alongside the existing fields — additive, non-breaking.
- **GET /api/notes** gains an optional `tagId` query parameter (FRS-NOTE-008, deferred from AB-1005): when supplied, the listing is restricted to the caller's active notes carrying that tag. `tagId` must reference a tag owned by the caller; an unowned or non-existent `tagId` is rejected `400 Bad Request` — matching how this endpoint already rejects invalid `page`/`pageSize`/`sortBy`/`sortDirection` rather than silently returning an empty page, and enforcing SDS §42 ("User A shall never be able to use User B's tag to access or discover User B's notes"). Supports exactly one `tagId` per request; multi-tag filtering is not introduced by this ticket. Existing pagination/sorting behavior and the response envelope shape are unchanged.
- New `Tag` EF Core entity + configuration + migration (SDS §15): `Id, UserId, Name, Color, CreatedAt, UpdatedAt`. A unique index on `(UserId, normalized Name)` enforces case-insensitive per-user uniqueness at the database level, not application-side-only.
- New `NoteTags` join table + configuration + migration (SDS §16): composite key `(NoteId, TagId)`, both FKs. Deleting a tag or a note's underlying row removes its `NoteTags` rows (FK cascade); soft-deleting a note does **not** remove its `NoteTags` rows (the association is preserved for restore).
- All eight endpoints (4 tag endpoints + the 4 touched note endpoints) use the standard Problem Details error contract (SDS §39) and require a valid JWT (`bearerAuth`), same pattern as AB-1004/AB-1005.

Out of scope for this ticket: multi-tag filtering (AND/OR across several `tagId` values); tag colors beyond `#RRGGBB` hex (e.g. named colors); any frontend tag UI (AB-1011/AB-1012); search (AB-1007); sharing (AB-1008); version history capturing tag assignments (AB-1009 — `NoteVersions` snapshots title/content only, per SDS §48, unchanged here).

## Capabilities

### New Capabilities
- `tags`: create, list (with per-tag note count), update, and delete a user's own tags — `openspec/specs/tags/spec.md` (new).

### Modified Capabilities
- `notes`: the **Note Creation** and **Note Update** requirements change to accept an optional `tagIds` array, validating every id against the caller's own tags before persisting. The **Note Listing** requirement changes to accept an optional `tagId` filter, validated the same way. All note response shapes gain a `tags` array.

## Impact

- **DB**: new `Tags` table (SDS §15) and `NoteTags` join table (SDS §16) + EF Core migration under `apps/api/src/NoteManagement.Infrastructure/Migrations`. Indexes per AGENTS.md §9: `Tags.UserId`, `Tags.UserId + Tags.Name` (unique, case-insensitive via a normalized computed/shadow column or a case-insensitive collation, decided in `/plan`), `NoteTags.NoteId`, `NoteTags.TagId`.
- **Domain**: new `Tag` entity (`apps/api/src/NoteManagement.Domain`), no ASP.NET Core dependency. `Note` entity gains a tag-assignment collection/method (exact shape decided in `/plan`).
- **Application**: new `TagService`/`ITagRepository` with create/list/update/delete use-cases, `CreateTagRequestDto`/`UpdateTagRequestDto`/`TagResponseDto`, validators (name length/trim, `#RRGGBB` format, case-insensitive duplicate check → `409`). `NoteService`/`INoteRepository`/note DTOs extended to accept and return `tagIds`/`tags`, validating ownership of every supplied tag id (`400` on any invalid id) before create/update; `NoteListQueryDto` gains `tagId`, validated the same way.
- **Api**: new `TagsController` with the four actions above, all `[Authorize]`. `NotesController`'s `Create`/`Update`/`List` actions extended to bind the new fields; `Get`/`Restore` response mapping extended to include `tags`.
- **Shared TS contracts**: `Tag`, `CreateTagRequest`, `UpdateTagRequest`, `TagListResponse` DTOs + mirrored Zod schemas added to `packages/shared` (AGENTS.md §12); existing `Note`/`CreateNoteRequest`/`UpdateNoteRequest`/`NoteListQuery` types extended additively with `tagIds`/`tags`/`tagId`, for later consumption by AB-1011/AB-1012.
- **Downstream dependencies**: AB-1007 (search) and AB-1009 (version history) are unaffected — neither currently indexes or snapshots tags. Any future multi-tag filtering or tag-based search remains an additive extension of the shapes established here.
- **Process**: `delta-openapi.yaml` for the four new tag endpoints and the four modified note endpoints is included in this change, required before `/plan` per AGENTS.md §8 / SDS §66.
